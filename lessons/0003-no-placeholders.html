No Placeholders：把 plan 从"看起来对"逼到"能交付"

这一关过不了，前面 brainstorming / worktree 做得再漂亮都是白搭 —— subagent 拿着模糊 plan，做出来的东西一定飘。

为什么这是使命 A 的分水岭

Mission tie-in

使命 A（把小产品送上线）：Step 3 (writing-plans) 是"能跑"和"能交付"的分界线。plan 里的每一个 TBD，都会在你不在场的时候被 subagent 用它自己的品味填掉 —— 那个品味不是你的。

使命 D（带团队）：一份团队 review 只需要看一条就能判断质量：这份 plan 里有没有 "appropriate" / "TBD" / "similar to" / "write tests for above"。有 = 退回；没有 = 值得细看。

Plan 的假想读者

SKILL.md 里那句话非常刻薄，但正是它撑起了整条 pipeline：

From writing-plans/SKILL.md

"Write comprehensive implementation plans assuming the engineer has zero context for our codebase and questionable taste. …Assume they are a skilled developer, but know almost nothing about our toolset or problem domain. Assume they don't know good test design very well."

中文直译：技术过硬 · 上下文为零 · 品味可疑 · 讨厌写测试的实习生。

这个画像听起来像在描述 subagent，但它也精确描述了团队里刚入职的同事。这就是为什么 writing-plans 是团队可复用资产的核心。你写的 plan，如果那个实习生照着做能出正确的软件，那 AI 也能。

Plan 骨架（30 秒）

完整模板在参考文档里。你只需要先记住：每份 plan 有 4 层结构：

  1. Header：Goal / Architecture / Tech Stack / Spec 路径（指向 Step 1 已批准的 spec 文件）
  2. Global Constraints：项目级红线（版本 / 依赖 / 命名）—— 每条从 spec 一字不差 copy
  3. Review Focus：spec 隐含但没 task 显式覆盖、最容易咬人的 5 类输入 —— 这个 section 是 superpowers 独有的东西
  4. 每个 Task：Files 块 · Interfaces 块（Consumes / Produces） · Step 1..N 每个 step 一个 checkbox + code block

No Placeholders · 六种失败

SKILL.md 里的 No Placeholders 段列了 6 种"plan 失败"，我把它们编号为 P1–P6，方便记忆：

编号症状为什么致命
P1 · TBDTBD / TODO / implement later / fill in details决策成本推给读者 = 没写。
P2 · 空泛add appropriate error handling / handle edge cases"appropriate" 是品味词，零上下文读者无法定义。
P3 · 无测试码Write tests for the above（不带测试代码块）测试设计 = 规格设计。没码 = 没规格。
P4 · 相似引用Similar to Task NExecutor 可能乱序读 task。冗余 ≠ 错误。
P5 · 只描述Code step 只说"做什么"不给 code block 说"怎么做"自然语言无法保证精确性。
P6 · 未定义符号引用了任何 task 都没定义的 类型/函数/方法凭空引用 = 幻觉。

反面示例 · 一份"看起来挺对"的坏 plan

下面是某个"用户注册 endpoint"的 plan 摘要。它同时踩齐了 P1–P6。花 3 分钟读完，找到每一处：

### Task 1: 骨架搭建 - 添加必要的依赖 (TBD: 版本) P1 - 建 RegisterController 空壳 ### Task 2: 写注册接口的实现 - Create: src/controllers/register.ts - Steps: - 写 register handler P5 - 添加 appropriate validation P2 - Write tests for the above P3 - Commit ### Task 3: 登录接口 - Similar to Task 2, but for login P4 - 使用 AuthService.validateAndIssue() P6 ### Task 4: 邮箱验证 - 处理各种 edge cases（重复邮箱 / 大小写 / 域名限制…） P2 - 添加错误处理 P2
如果这份 plan 交给 subagent，会发生什么

Task 1 里的 TBD: 版本 → 第一个 subagent 会挑一个它训练时最常见的版本；Task 2 里的 appropriate validation → 第二个 subagent 会加一份它自己觉得合理的正则；Task 3 里的 AuthService.validateAndIssue() → 没有任何 task Produces 过它，第三个 subagent 只能自己造一个 —— 于是 Task 4 引用的又是另一个。

结果：4 个 task 各自能编译过，但接口对不上，集成时炸。

正面示例 · Task 2 重写

把 Task 2 按 writing-plans 的模板重写一遍，你会看到具体到什么程度：

### Task 2: 注册接口的 email + password 校验 **Files:** - Create: src/controllers/register.ts - Create: tests/controllers/register.test.ts **Interfaces:** - Consumes: (无 —— 这是第一个 controller) - Produces: - `register(req: {email: string, password: string}) -> {ok: true, userId: string} | {ok: false, error: 'INVALID_EMAIL' | 'WEAK_PASSWORD'}` - [ ] **Step 1: 写失败测试（3 个 case）** ```ts // tests/controllers/register.test.ts test('rejects email without @', async () => { const r = await register({ email: 'foo', password: 'supersecret123' }); expect(r).toEqual({ ok: false, error: 'INVALID_EMAIL' }); }); test('rejects password shorter than 12 chars', async () => { const r = await register({ email: 'a@b.co', password: 'short' }); expect(r).toEqual({ ok: false, error: 'WEAK_PASSWORD' }); }); test('accepts valid input and returns userId', async () => { const r = await register({ email: 'a@b.co', password: 'supersecret123' }); expect(r.ok).toBe(true); expect(typeof r.userId).toBe('string'); }); ``` - [ ] **Step 2: 跑测试确认失败** Run: `npm test -- tests/controllers/register.test.ts` Expected: 3 failures with "register is not a function" - [ ] **Step 3: 写最小实现** ```ts // src/controllers/register.ts export async function register(req) { if (!req.email.includes('@')) return { ok: false, error: 'INVALID_EMAIL' }; if (req.password.length < 12) return { ok: false, error: 'WEAK_PASSWORD' }; const userId = randomUUID(); await db.users.insert({ id: userId, email: req.email, hash: await bcrypt.hash(req.password, 12) }); return { ok: true, userId }; } ``` - [ ] **Step 4: 跑测试确认通过** - [ ] **Step 5: Commit** ```bash git add src/controllers/register.ts tests/controllers/register.test.ts git commit -m "feat(register): add email+password signup with validation" ```

关键差异：

  • 错误字符串（INVALID_EMAIL、WEAK_PASSWORD）被 显式列入 Produces —— 后面任何 task 引用它，都有出处（对 P6）
  • 3 个测试 case 都写了代码 —— 规格 = 测试代码（对 P3、P5）
  • 没有 "appropriate" / "handle edge cases" 这种词 —— 只有具体输入 + 具体断言（对 P2）
  • Step 5 里连 git add 的路径都写死了（对 P1）

Self-Review 4 项（写完后必做）

SKILL.md 明列这 4 项，由 plan 作者自己 inline 完成（不是派 subagent 做）：

检查问什么
① Spec coveragespec 里每条要求，能不能指到一个 task？列表化未覆盖项。
② Placeholder scan整份 plan 扫一遍 P1–P6。
③ Type consistencyTask 3 叫 clearLayers()、Task 7 叫 clearFullLayers() = bug。签名前后必须一致。
④ Review Focusspec 隐含的失败模式，每个都有对应 task 的测试覆盖了吗？空 section 意味着"我查了没有"，不是"我跳过了"。
发现问题怎么办

Inline 改掉，不用再走一次 review。发现 spec 有要求但 plan 无 task → 补上 task。

行动：30 分钟内做一次 plan 体检

Action Step · 手上有旧 plan 就用它，没有就现造

路径 A · 手上有旧 plan（比如你之前在某个项目里让 agent 生成过的 plan）：

  1. 打开它，用P1–P6 清单逐行标注：找到每一个 TBD / "appropriate" / "similar to Task N" / "write tests for above" / 无 code block 的 code step / 未定义符号。
  2. 数一下总数。少于 3 处 → 你运气不错；多于 10 处 → 这就是 subagent 之前跑偏的原因。
  3. 挑其中最刺眼的一个 task，按 正面示例 的格式重写它。贴给我看。

路径 B · 没有旧 plan：

  1. 给你小产品随便挑一个真实 feature（比如"注册 endpoint"、"上传一张图片"）。
  2. 先按你自己的直觉写 3 个 task 的 plan —— 故意写松一点。
  3. 自己走 P1–P6 扫一遍，把 5 个以上的失败改到最小可交付版本。
  4. 改前 + 改后都贴给我 —— 我会写 learning-record 0001 记录你的判断力。

如何给同事讲这件事（评审用 · 3 分钟）

可复制到 team wiki 的一段话

"审一份 AI 或同事写的 implementation plan，你不需要读完全部代码。只要用眼睛扫这 4 个词组，就能判断它是不是"能交付"：

  • TBD / TODO / implement later —— 出现 = P1，退回。
  • appropriate / edge cases / as needed —— 出现 = P2，退回。
  • Similar to Task N —— 出现 = P4，退回。要求把代码重抄。
  • Write tests for the above 但看不到测试代码 = P3，退回。

这四条命中任意一条，你都可以不继续往下读：它还没准备好被 subagent 或新入职同事执行。改完再来。

反过来，一份合格的 plan 应该长这样：每个 task 有明确的 Consumes / Produces，每个 code step 有代码块，每个测试断言具体到字符串。看起来会有点冗长 —— 那个冗长就是它能被交付的代价。
