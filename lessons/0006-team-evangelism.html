团队布道：30 分钟把 superpowers 讲给同事

整合课。你学到的不是新知识，是"如何把 0001–0005 讲给别人听 · 应对 5 种抵触 · 度量推行是否成功"。

使命 D 的终点检验

Why this lesson exists

你之前答 mission 时选了 "D · 带进 2-10 人小团队"。团队布道的失败方式非常固定：不是同事不聪明，是你没准备好他们要问的 5 个反驳。这一课把这些反驳列出来，配上应答。

30 分钟培训脚本

时段做什么要点
0–5 min 一个失败案例 找一个大家都熟的 project · 展示一次"AI 帮我做但结果很烂"的具体片段。不要一上来讲 superpowers。先让所有人同意"直接让 AI 写代码确实有问题"。
5–15 min 白板画 pipeline 画 7 步流水线（0002）。每步一句话说它在解决什么失败。重点讲 Step 1 的三路分类（0001）—— 因为团队最容易问的"这么小也要写 spec"就是这里回答。
15–25 min Live demo 用真实小需求（比如给内部工具加一个导出 CSV 按钮）跑一遍 brainstorming。让同事看到 agent 反问 —— 那一瞬间的惊讶是布道的最大杠杆。不要跑完整条 pipeline，那要 2 小时。
25–30 min 承诺 + 拒绝 承诺：给一个"3 天试用窗口"，其间用 superpowers 干的所有活可以走回头路、允许失败。拒绝：不承诺全公司 all-in。给同事的最低行动："下次让 AI 帮你写代码时，先跑一次 brainstorming，就一步。"

5 种团队抵触 · 应答

这些不是我编的，是 superpowers 引入团队时最典型的 5 句话。每一句对应一课的某个点。

抵触 1 · "就这么个小活儿，也要走完整流程？"

应答（来自 0001）

"不需要。Superpowers 有三路分类：Spike · Bounded · Architectural。判据不是任务大小，是'这条流程现在在仓库里能读到吗？'能读到 → Bounded，chat 里两句话说清就可以直接动。读不到、要留下来的代码 → 那才是 Architectural。"

抵触 2 · "我 prompt 已经写得很清楚了，agent 直接干就完了。"

应答（来自 0003）

"Prompt 感觉'清楚'和 plan 真的'能被零上下文执行'是两回事。检验方法：你打开你的 prompt，扫这 4 个词组 —— TBD / appropriate / similar to Task N / 写测试处理上面那个。任何一个出现 = 你其实没定完，只是感觉定完了。superpowers 的 plan 结构就是把这些逼出来。"

抵触 3 · "AI 说完成了，那就完成了呗，为什么我还要跑一遍？"

应答（来自 0005）

"因为 AI 会说 'tests pass' 但其实根本没跑过 —— 是它上一次 session 的记忆在骗它。Superpowers 有一条铁律：没有刚跑出来的证据，不许说完成。你作为 reviewer 只需要问一句：『最后一次 commit 之后你跑过测试吗？贴一下输出。』这一句能筛掉 80% 的假绿。"

抵触 4 · "这也太啰嗦了，效率明显降低。"

应答（来自 0002 + 0004）

"前 30 分钟是慢，因为你欠着 spec 和 plan。但一旦 plan 定完，subagent 可以无人值守跑 2 小时 —— 这段时间你的效率是原来的 5-10 倍。整体看下来：一次性大 feature 用 superpowers 更快；琐碎改动用 superpowers 更慢，那种时候直接改就好。别拿错工具。"

抵触 5 · "subagent 听起来很高级，我们是不是所有活都开它？"

应答（来自 0004）

"反过来 —— subagent 不是更高级，是更贵。它烧 2× token 换两样东西：task 之间通过 plan 的 Interfaces 块强制契约 · 每个 task 不被上一 task 的上下文污染。什么时候用：Task ≥ 10 · 出错代价高 · 需要长时间无人值守。小 plan + 预算紧 → 用 native。"

度量：什么算"推行成功"

不要以"团队都装了 superpowers"为成功标准 —— 那只是安装量。真正的度量：行为变化。

信号说明什么观察周期
同事提交 PR 时描述里贴了测试运行输出Verification Iron Law 内化了2 周
有人在群里说 "这是 Bounded 还是 Architectural？"三路分类成了团队词汇1 个月
同事主动问 "这次要不要 subagent？"执行模式成为决策项1-2 个月
新人第一天就能用 brainstorming 独立跑一个 feature整套方法成了默认路径3 个月
同事开始质疑你的 plan 里的 P1-P6布道完成 —— 团队有了共同品味3-6 个月
最不应该追的指标

不要追 "每人日均 AI 生成代码行数" —— 那会激励跳过 pipeline。追 "bug 从发现到修复的时间"：superpowers 的 TDD + verification 会把这个数字压下去。这才是团队老板会认的 KPI。

Demo 脚本：现场跑 brainstorming

培训第 15 分钟那段 demo，用下面这个脚本可以几乎必然让同事"哦"一声：

  1. 打开 Claude Code / Qoder · 已安装 superpowers
  2. 输入这句话（不要改）：
    让我们做一个 React 的 TODO 列表
  3. 什么都不做。让 agent 自己触发 brainstorming。
  4. 同事会看到 agent：
    · 说 "this looks architectural, so I'll..." —— 三路分类的显式口播
    · 反问一个关于 purpose 的问题（不是马上写代码）
    · 一次只问一个问题
  5. 关键讲解点："你注意到它没直接开始写吗？它先做了分类，然后开始问问题。这一步就是 superpowers 全部价值的入口。"
Demo 之前必做的准备

确保你的 superpowers 是最新版的（README 提到 验证方式：fresh session 输入 "Let's make a react todo list" 会自动触发 brainstorming）。如果没触发，先跑 diagnosing-superpowers 修好，别在同事面前翻车。

行动：排出你的 30 分钟培训

Action Step · 30 分钟准备

  1. 打开日历 · 定一个真实的时间（不是"以后再说"）· 未来 2-4 周内 · 团队 30 分钟。
  2. 填这四栏：
    · 失败案例（0-5min）：具体到哪个 sprint、哪个 PR、当时谁的判断。
    · Demo 需求（15-25min）：现场要跑的那一句 prompt 是什么。
    · 试用承诺（25-30min）：给团队多长的试用期？失败允许走回头路吗？
    · 度量约定：30 天后你打算问同事哪 3 个问题判断是否推行成功？
  3. 把这份填好的 1-pager 打印或存成 wiki 页面 —— 参考模板。
  4. 把这份计划贴给我 —— 我会给你 feedback + 写 learning-record。
