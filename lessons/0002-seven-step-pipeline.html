7 步流水线全景

当 agent "跑偏"时，绝大多数情况是它在流水线里跳了一格，或把两格并成了一格。这一课给你一张能定位问题的地图。

为什么现在讲这个

上一课的三路分类是 Step 1 内部的判断。这一课把镜头拉远，看整条流水线。

Mission tie-in

使命 A（做小产品）：你会在第 3–6 步之间反复待几个小时。认得出自己在哪一格，才知道下一步该给什么输入。

使命 D（带团队）："白板讲 7 步" 是 superpowers 布道的开场动作。讲不清这 7 步 = 同事只会把 agent 当 ChatGPT 用。

地图

superpowers 官方 README 里 The Basic Workflow 定义了 7 步：从 brainstorming 到 finishing-a-development-branch。完整表格在参考文档里，先看一句话版：

  1. brainstorming —— 从需求中"炼"出设计（三路分类在这）
  2. using-git-worktrees —— 建隔离工作区 + 跑一次基线测试
  3. writing-plans —— 把设计拆成 2–5 分钟一步的 bite-sized 任务
  4. subagent-driven-development 或 executing-plans —— 选执行模式
  5. test-driven-development —— RED → GREEN → REFACTOR，在每个 task 内
  6. requesting-code-review —— 在 task 之间，对照 plan 评审
  7. finishing-a-development-branch —— 呈现 merge / PR / keep 三选一，由人决定

三个反直觉的点

背下来 7 步不难，难的是不被直觉骗到。三处最容易讲错给同事：

① 流水线不是直线：4/5/6 是嵌套循环

常见误解

"我先跑完所有 task（第 4 步），再补 TDD 和 code review。" —— 错。

第 4 步是外层策略（选 subagent 还是 native）；第 5 步 test-driven-development 和第 6 步 requesting-code-review 是每个 task 内 / task 之间各跑一次。也就是说：单个 task 的循环长这样：

Task N:
  → RED：写一个会失败的测试，跑，看它失败
  → GREEN：写最小实现，跑，看它通过
  → REFACTOR
  → commit
  → code review（对照 plan 检查这个 task）
    → 通过才允许进 Task N+1
    → Critical 问题 = 阻塞前进

② 第 4 步有岔路：Subagent 还是 Native

这不是"哪个更高级"的问题，是成本 vs 独立性的取舍。一手定义在 writing-plans 尾部 Execution Handoff 段：

Subagent-drivenNative (executing-plans)
每 task 用新 subagent 实现 + 新 reviewer 评审本 session 直接实现
独立评审每 task 都有 · 最后再整枝只在最后整枝一次
Token 成本高低
适合task 间接口复杂 · 出错代价高 · 长时间无人值守plan 已经把设计说透 · 中等模型够用

Agent 会在 plan 结束时问你选哪个。不要闭眼选 subagent：一个 3 task 的小 feature 用 subagent 是浪费；一个 30 task 的骨架改动用 native 是让 bug 藏到最后一关。

③ 第 7 步的 3 选项：菜单属于人

finishing-a-development-branch 在测试全绿之后必须呈现这个菜单：

Implementation complete. What would you like to do?
1. Merge back to <base-branch> locally
2. Push and create a Pull Request
3. Keep the branch as-is (I'll handle it later)

Which option?
Agent 常见的越权

"测试都过了我这就 merge。" —— 停。SKILL.md 明确列出反模式："They obviously want it merged" → Integration is your human partner's decision.

Discard 更严格：只有你亲手敲 discard 这个词才算授权。"看起来他不想要了" 不算。

行动： Mental walkthrough · 10 分钟

Action Step · 今天/明天做

想象你的 使命 A 的那个小产品（还没告诉过我具体是什么 —— 现在在心里定一个方向即可）。用 5 分钟在纸上按下面 7 栏填一遍：

  1. Step 1：brainstorming 三路里我会走哪一路？为什么？（预期 = Architectural，因为 repo 里它还不存在）
  2. Step 2：我的项目主分支是 main 还是 master？基线测试怎么跑？（写死命令）
  3. Step 3：我预计第一个 plan 会被拆成几个 task？（不用真拆，猜一个数）
  4. Step 4：这个产品第一次跑，我倾向 subagent 还是 native？为什么？
  5. Step 5：我熟悉的测试框架是什么？RED-GREEN 循环我知道怎么手动跑一次吗？
  6. Step 6：Task 之间的 code review 我会看什么？（对照 plan？看接口一致性？）
  7. Step 7：完成后我打算 merge 到本地还是开 PR？（前者= solo，后者=给团队看，与 mission D 直接相关）

写完后把这张纸拍照或直接文字整理贴给我 —— 我会据此写 learning-records/0001-...，并调整 0003 的深度。

如何给同事讲这件事（白板版）

可复制到 team wiki 的一段话

"Superpowers 把'让 AI 帮我写代码'拆成 7 站。你可以把它想成一条流水线：设计 → 隔离 → 拆任务 → 执行 → 每步 TDD → 每步评审 → 最后人来决定怎么合。

三个必须记住的点：

  • 它 不是 一条直线。第 5 步 TDD 和第 6 步 review 是在每一个 task 里/之间各跑一次的 —— 不是最后统一补。
  • 第 4 步有岔路：可以让每 task 都由 fresh subagent 做（贵但彻底），也可以本 session 一路推完再评审（省 token）。选哪个是你的决定，不是默认。
  • 第 7 步的 merge / PR / keep 三选一，是人选的。如果哪天 agent 测试绿了就自己 merge 了 —— 那是 bug，回来告诉我。

一句话总结：7 步流水线不是 bureaucracy，每一步背后都是一个具体的失败模式。
