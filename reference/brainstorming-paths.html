Brainstorming 三路分类 · 速查表

Spike / Bounded / Architectural —— 一手来源：skills/brainstorming/SKILL.md

三路卡片

Path A

Spike

输出是答案，不是代码。

触发词："能不能……"、"试试是否……"、"quick and dirty is fine"。

做法：2-3 句说清 probe，用户点头就跑；产物是 recommendation。

Artifact：口头/一段文字结论。所有代码标 throwaway。
Path B

Bounded

改动的是仓库里已有的流程。

加个 flag、加个小 endpoint、单文件 fix。前提：这条流"已经在这里可以读"。

做法：问几个关键问题 → 在 chat 里给一段短设计 → STOP 等 yes → 直接实现（仍走 TDD）。

Artifact：chat 里的短设计。没有 spec 文件、没有 plan 文档。
Path C

Architectural

新项目 / 新子系统 / 会改变接口拓扑。

判据：仓库里没有既存的流程可以照着改。

做法：完整链路 —— 探context → 一次一问澄清 → 2-3 方案对比 → 分段呈现设计并逐段确认 → 写 spec 文件 → 用户 review spec → 交给 writing-plans。

Artifact：docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md。

决策的一刀切

问自己：「这条流程现在在这个 repo 里能读到吗？」

答案路径
不 —— 这是全新东西Architectural
是 —— 只是加/修一小块Bounded
不 —— 我只想验证一个"能不能"Spike
在两者之间犹豫时

走重的那条。 伸手拿 "bounded" 这个标签来跳过工作，这个动作本身就是 doubt 的信号。

棘轮规则（Ratchet）

单向棘轮

任务中途发现隐藏复杂度 → 升级路径（spike→bounded→architectural）。停下来，说出来。

没有任何情况允许降级。"快做完了不用重新分类" = 反模式。

HARD-GATE：批准 ≠ 一次授权全部

brainstorming 的 <HARD-GATE> 定义："批准"只针对当前呈现出来的那一层：

路径闸门 = 谁的哪个批准
Spike人类 partner 批准 问题 + probe 计划
Bounded人类 partner 批准 chat 里那段短设计（呈现设计和开始动手必须分成两个消息）
Architectural两级：会话设计批准 → 才允许写 spec 文件 → spec 文件批准 → 才允许调用 writing-plans
关键反模式

"I understand this kind of app, so it's bounded" —— 错。Bounded 度量的是仓库，不是你的熟悉度。一个 todo app 你写过一百次也一样是 Architectural，因为这个 repo 里它还不存在。

Red Flags 对照表（一手翻自 SKILL.md）

脑中的念头真相
"太简单了不用设计"按选中的路径走。Bounded 只要 chat 里两句话；Architectural 就要 spec 文件。
"我叫它 bounded 就能跳过 spec"这个念头本身 = doubt → 走重的路径。
"设计明显，我边说他边看边写"闸门是"批准"，不是"设计长度"。呈现后要 STOP。
"我熟这类 app，所以是 bounded"Bounded 度量仓库，不度量熟悉度。
"spike 跑通了，代码留下吧"Spike 的产物是答案。留代码是新需求 → 重新分类。
"它变复杂了但我快做完了"中途升级 ≠ 重做，只 = 停下来重新走一次分类。
"他批准了 spike，那后续改动也算批了"每个任务有自己的分类和自己的批准。

终点状态（Terminal State）

路径brainstorming 结束后唯一能调用的下一步
Spike报告 recommendation。没有下一步。
Bounded直接进入 normal dev workflow（TDD）——没有 plan 文档。
Architectural唯一出口：writing-plans。
禁止直接叫 frontend-design / mcp-builder 等实现类 skill。
