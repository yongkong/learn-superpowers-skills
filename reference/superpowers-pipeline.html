Superpowers 7 步流水线 · 速查图

一手来源：README · The Basic Workflow。当 pipeline 定义变化时以 README + 各 SKILL.md 为准。

七步一屏

#Skill激活时机退出闸门（Artifact / 批准）
1 brainstorming 写代码之前 · 永远第一个 三路路径各自批准：Spike=recommendation；Bounded=chat 短设计；Arch=已 review 的 spec 文件
2 using-git-worktrees 设计批准之后 隔离工作区就绪 · 项目 setup 已跑 · 测试基线全绿
3 writing-plans 有已批准的设计 plan 文档 · 每个 task 是 2–5 分钟的一步 · 无占位符 · 用户选择执行方式
4 subagent-driven-development 或 executing-plans 有已批准的 plan Subagent：每 task 一个新 agent + 一次 review
Native：本 session 一把梭 + 最后整枝 review
5 test-driven-development 第 4 步执行期间 · 每个 task 内 RED → GREEN → REFACTOR · 先看失败再看通过 · 提前写的代码删除
6 requesting-code-review Task 之间 对照 plan 评审 · 按严重性报问题 · Critical 阻塞下一步
7 finishing-a-development-branch 所有 task 完成 整套测试重跑通过 · 呈现 3 选项菜单 · 由人类选（merge / PR / keep）

流水线不是直线

Step 4 · 5 · 6 是嵌套循环

Subagent / Native 是外层策略；TDD 和 code-review 是每个 task 里跑一次。
不是"先做完所有 task，再补 TDD 和 review"。

Step 4 的岔路：Subagent vs Native

Mode A · 最彻底

subagent-driven-development

每个 task 派一个新 subagent 实现 · 实现完立刻派另一个 agent 评审 · 两阶段 review（spec 合规 → 代码质量）· 最后整枝 review。

成本：每 task 一次 fresh context + 每次评审一次 fresh context。token 消耗最大。

适合：task 间接口复杂 · 出错的代价高 · 需要长时段无人值守。

Mode B · 最省

executing-plans (native)

本 session 内一路把 task 全实现 · 最后请一个更强模型的 reviewer 走一遍整枝。

成本：只在结尾一次独立评审。

适合：plan 已经把设计说透 · 中等模型也够用 · 独立性要求不那么高。

每一步的"退出闸门"为什么存在

Step如果没有这一步，会出什么问题
1 brainstormingAgent 直接猜你要什么 → 做出来的东西不是你要的。且没有 spec 文件作为团队共识锚。
2 using-git-worktrees失败改动污染主分支 · 中途 revert 昂贵 · 没有"测试基线全绿"意味着后续任何红色都不知道是新引入的还是本来就有的。
3 writing-plansAgent 走一步看一步 → 中途方向偏移无法察觉 · subagent 无法被"零基础"执行。
4 执行模式选择要么过度使用 token（该 native 时用了 subagent），要么评审不足（该 subagent 时用了 native）。
5 test-driven-development"写完代码补测试"= 测试跟着实现走 · 只覆盖了你已经做对的部分。
6 requesting-code-review错误累积。第一个 task 判断错 → 后面所有 task 建立在错误接口上。
7 finishing-a-development-branchAgent 自作主张 merge / push / 丢弃 · 集成决策本属于人。

异常诊断入口

当 session 表现不对（skill 没触发、agent 越闸门、烧 token 过快、重复劳动）→ 让 agent 调用 diagnosing-superpowers。它会读 session transcript · 报出行级证据 · 并可以打包脱敏 bundle 报到 GitHub Issues。
