### Task N: [组件名]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test:   `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [此 task 用到前面 task 的什么 · 精确签名]
- Produces: [后面 task 依赖此 task 的什么 · 精确函数名/参数/返回]

- [ ] **Step 1: Write the failing test**
      ```python
      def test_specific_behavior(): ...
      ```
- [ ] **Step 2: Run test to verify it fails**
      Run: `pytest tests/... -v`
      Expected: FAIL with "..."
- [ ] **Step 3: Write minimal implementation**
      ```python
      def function(input): ...
      ```
- [ ] **Step 4: Run test to verify it passes**
- [ ] **Step 5: Commit**
      ```bash
      git add ... && git commit -m "feat: ..."
      ```

Task 粒度：2-5 分钟一步

一个 step = 一个动作。参考切法：

  • "写失败的测试" —— 一步
  • "跑测试确认它失败" —— 一步
  • "写最小实现" —— 一步
  • "跑测试确认通过" —— 一步
  • "commit" —— 一步

Task 边界原则（Task Right-Sizing）：把 setup / config / scaffolding / docs 折进它服务的 deliverable 所在 task；只在"评审者可能批准 A 但否决 B"的地方拆 task。每个 task 以一个可独立测试的 deliverable 结尾。

No Placeholders · 六种 plan 失败

编号症状（原文样本）为什么是失败
P1 · TBD "TBD" / "TODO" / "implement later" / "fill in details" 把决策成本推给读者，等于没写。
P2 · 空泛 "Add appropriate error handling" / "add validation" / "handle edge cases" "appropriate" 是品味词，零上下文读者无法定义。必须写出具体错误、具体输入、具体断言。
P3 · 无测试代码 "Write tests for the above"（不带测试代码块） 测试设计是 plan 的核心，不是可选附件。没代码 = 没规格。
P4 · 相似引用 "Similar to Task N" Executor 可能乱序读 task。要重抄代码 —— 冗余 ≠ 错误。
P5 · 只描述不给码 步骤说"做什么"但没有 code block 说"怎么做" Code step 必须含 code block。描述性语言无法保证精确性。
P6 · 未定义符号 引用了任何 task 都没定义的 类型 / 函数 / 方法 接口的存在必须被某处 Produces 声明。凭空引用 = 幻觉。

Self-Review 4 项（写完后自查）

SKILL.md 明列这 4 项 —— 不是可选题。由你自己 inline 检查，不派 subagent：

  1. Spec coverage：spec 里每条要求，能不能指到一个 task 实现它？列表化未覆盖项。
  2. Placeholder scan：整份 plan 扫一遍 6 种失败（P1–P6）。
  3. Type consistency：Task 3 里叫 clearLayers()，Task 7 叫 clearFullLayers() = bug。前后签名必须一致。
  4. Review Focus：spec 隐含的失败模式，是否每个都有一 task 覆盖？空 section 意味着"我查了没有"，不是"我跳过了"。
修 Just-in-time

Self-review 发现问题 → inline 改掉，不用再走一次 review。发现 spec 有要求但 plan 无 task → 补上 task。

Execution Handoff（Step 4 岔路）

Plan 保存后，agent 会让你在两种执行方式里选：Subagent-driven（每 task fresh agent + fresh reviewer + 最后整枝 review · 最彻底 · 最贵）或 Native（本 session 一路推完 + 最后整枝 review · 最省）。选前 agent 应给出基于此 plan 具体特征的推荐（依赖密度 · task 数 · 出错代价）。

这也是为什么 Interfaces 块（Consumes/Produces）在 subagent 模式下几乎是 plan 的生死线 —— 每个 fresh subagent 只看到自己那一个 task，别的都看不到。没有 Interfaces 块，它们就没办法对齐接口签名。
