Verification Before Completion：证据先于声明

Agent 说"搞定！测试通过！" —— 它跑过吗？没跑过 = 在骗你，哪怕它自己没意识到。

为什么这一课最"轻"却最重要

Mission tie-in

使命 A：小产品能上线的前提是 —— 你说"能上线"这件事本身是可验证的。Verification 不是流程洁癖，是把"我以为好了"变成"这是刚刚跑出来的日志"。

使命 D：团队里 AI 生成的 PR 最大风险不是"代码写得烂"，是"看起来完成了其实根本没跑过测试"。这一课的 Iron Law 是团队 PR review 的第一条规则。

Iron Law

The Iron Law

NO COMPLETION CLAIMS
WITHOUT FRESH VERIFICATION EVIDENCE

如果你本条消息内没跑过验证命令，你不能声称它通过。

注意"fresh"（新鲜）：上一轮跑过不算数。你刚改了 3 个文件，之前那次绿色测试已经过期了。

Gate Function：5 步流程

任何"我状态如何 / 我很满意 / 搞定了"的表达之前，必须先走完 5 步：

  1. IDENTIFY：什么命令能证明这个声明？
  2. RUN：完整跑一遍（fresh、不缓存、不跳过）
  3. READ：读完整输出 · 看 exit code · 数 failures
  4. VERIFY：输出真的支持这个声明吗？
    · 不支持 → 说实际状态 + 证据
    · 支持 → 声明 + 证据一起说
  5. ONLY THEN：做出这个声明
跳过任何一步 = 撒谎

SKILL.md 原文："Skip any step = lying, not verifying." 语气很重。因为 AI agent 最常见的失败不是"跑不过"，是"以为自己跑过了"。

常见失败对照表

声明需要什么证据什么不算数
"测试通过"测试命令输出：0 failures上一次跑过 · "应该会过"
"linter 干净"linter 输出：0 errors只跑了部分文件 · 靠推测
"build 成功"build 命令：exit 0linter 过了（≠ 编译过） · 日志看着没事
"bug 已修"原症状的复现命令：现在 pass改了代码 · 假设修好了
"回归测试有效"Red-Green 双向验证 · revert 后必须 fail测试通过一次（可能是 false green）
"subagent 完成了"VCS diff 显示改动Agent 自报 success
"需求都满足了"逐条 plan checklist 对照验证"测试通过 = phase 完成"

Red Flags · 一句话识别

任何下列念头出现 → 停：

  • 你正在说 "should"、"probably"、"seems to"、"看起来"
  • 验证还没跑就已经在 "Great!" / "Perfect!" / "Done!"
  • 即将 commit / push / 提 PR 但没跑验证
  • 相信 subagent 的自报"成功"
  • 只跑了部分验证但打算声称全部通过
  • "就这一次"心态
  • 你累了，想赶紧收工
最阴险的一条

"用了不同的措辞所以规则不适用。" —— 不对。Iron Law 覆盖 字面 / 换词 / 隐含的成功暗示。你说"这版应该可以上线了"= 你在做完成声明 = 需要证据。

对 AI agent 特别重要的两条

① 不要相信 subagent 的 "success report"

Subagent 会说："我做完了 · 测试通过"。那是它的自报。Verification 要求你去 git log 看 commit · 去跑一遍测试 · 看 diff。SKILL.md："Agent completed → VCS diff shows changes · Not Sufficient: Agent reports success."

② Regression test 必须双向验证

只看到测试通过不能证明它能捕获 bug。真正的做法：

写测试 → 跑（通过）
revert fix → 跑（必须 FAIL） ← 这步不做 = 你不知道测试是不是 false green
restore fix → 跑（通过）

少了中间那一步，测试只是"跟着代码跑绿灯"，没有保护力。

行动：审计你的最近一次 session

Action Step · 10 分钟

1. 打开你最近一次让 agent 帮你写代码的 session 记录（或你自己最近 3 条 commit）。

2. 找 3 处 "未验证的成功声明"：任何"看起来 / 应该 / 搞定了 / 完美"的措辞，但没有紧跟一条实际跑过的命令输出。

3. 对每一处问自己：如果这个 bug 上线，成本是什么？

4. 把 3 处发现写下来 —— 会成为 learning-record。之后你的默认反应会从"agent 说完成 → 我信"改成"agent 说完成 → 我要求证据"。

如何给同事讲这件事

可复制到 team wiki 的一段话

"Superpowers 里有一条铁律：没有刚跑出来的证据，不许说完成。具体到工程习惯就三句：

  • 任何 'should / probably / 看起来 / 应该 ok 了' = 红旗，说明还没跑。
  • AI 报告"我完成啦"不算证据 —— 去看 git diff、去本地跑测试。
  • 回归测试必须能真的失败（revert 修复 → 测试必须变红）才算它有效。

PR review 时，你只需要问作者一句：『最后一次 commit 之后你跑过测试吗？贴一下输出。』 一句话筛掉 80% 的假绿。"
