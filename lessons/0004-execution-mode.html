执行模式岔路：Subagent-driven vs Native

"能不能让 agent 无人值守跑两小时" —— 答案不在模型多强，在你 plan 写得多具体 + 选了哪种执行模式。

为什么这是最重要的一课

Mission tie-in

使命 A：你想把小产品送上线，最宝贵的资源是你的时间。选对执行模式 = 一晚上跑完 20 个 task；选错 = 半夜醒来发现 agent 卡在第二个 task 的接口不匹配。

使命 D：团队最容易问的一句 —— "为什么我要用 subagent，直接一个 prompt 让 AI 全写完不行吗？" 这一课给你答案。

两种模式的定义

Mode A · 最彻底

subagent-driven-development

每个 task 派 fresh implementer subagent · 实现完 fresh task-reviewer 评审 · spec 合规 + 代码质量两关都过 · 才允许下一 task · 最后 whole-branch reviewer 收尾。

成本：每 task 至少 2 份 fresh context。

Mode B · 最省

executing-plans (native)

本 session 一路把所有 task 都实现 · 结束时一个更强模型 reviewer 走一遍整枝。

成本：一份 session context + 一份最后 reviewer。

两者都不是默认的"更高级 vs 更低级" —— 是成本 / 独立性 / 上下文长度的三维取舍。

Subagent 的 3 个隐藏机制

README 只讲了一句话："每 task 一个 subagent + 每 task 后一次评审"。真正跑起来靠的是 subagent-driven-development 里的三条硬约束：

① 台账（Ledger）：跨 compact 恢复

Session 会 compact（上下文压缩），对话记忆会丢。SKILL.md 明说："Conversation memory does not survive compaction. In real sessions, controllers that lost their place have re-dispatched entire completed task sequences." 每个 plan 拥有一个 workspace 里的 progress.md 台账，记录每个 task 的完成 commit。Compaction 之后：相信台账 + git log，而不是相信你自己的记忆。

② 裁决，不暂停（Rulings, not stalls）

Subagent 跑起来时遇到冲突 / 歧义 / plan 缺陷，不停下来问你。SKILL.md 的原话："A wrong ruling costs rework your human partner can see and undo; a session parked on a question costs their whole day and buys nothing." Agent 会：把裁决写进台账 → 继续跑。你回来后可以看到"这里我判了 X 因为 Y，代价 Z"。

③ 4 个真正的暂停条件

Subagent 只会因为下面 4 种情况停下来问你：

  1. 不可逆 / 破坏性操作
  2. 安全敏感动作
  3. Worktree 之外的副作用（merge / push 到共享分支 / publish）
  4. Plan 已经烂到"任何方向都是猜"

除此之外 不许停。"要继续吗？" 这种问句被明确列为浪费你时间的行为。

Native 模式不是"随便做做"

Native 的对应 skill 是 executing-plans。它同样要求：plan 是权威 · 每 task 走完 · 最后必须有 独立 的 whole-branch reviewer（不是自己审自己）。区别只在于：中间没有 fresh context，所以整个 session 是一个人的连续工作记忆。

Native 的失败模式

Task 5 的一个错误决定会污染 Task 6–20 的上下文 —— 因为"你之前也是这样做的"。Subagent 天然免疫这个，因为每个 subagent 只看自己那 task 的 brief。Native 免疫不了。

经验法则

Task 数量 × 出错代价 / token 预算 ≥ 1 → Subagent。
≤ 5 个 task 且都在同一份既有代码里挪 · Native。

如何给同事讲这件事

可复制到 team wiki 的一段话

"Superpowers 有两条实现路径：Subagent（每个 task 一个新 agent 实现 + 一个新 agent 评审）和 Native（本 session 一路推完 + 最后整枝评审）。

Subagent 不是更高级，是更贵。它烧 2× token 换两样东西：Task 之间接口通过 plan 里的 Interfaces 块 强制契约 · 每个 task 的错误判断不会污染下一个 task。

什么时候用：Task ≥ 10 · 出错代价高 · 需要长时间无人值守。什么时候不用：小 plan · 预算紧 · 设计已经定得死死的。

Subagent 有一个反直觉的规则：它跑起来时不问你问题。碰到 plan 里的冲突，它自己裁决、写进台账、继续跑。只有 4 种情况会真停下来：不可逆操作 / 安全 / 影响 worktree 外（比如 push 到共享分支）/ plan 烂到没法继续。也就是说 —— 你回来后能看到它每一个判断，但不会被打扰。"
