Superpowers · 团队布道 1-pager

A4 双面打印版。培训当天贴在会议室 / 存到 team wiki / 附在会议邀请里。

为什么要它

直接跟 AI 说"帮我做个 X"，最常见的 3 种翻车：

  • 做出来了，但不是你要的 —— 因为需求没定完
  • 看起来跑通了，一上线就炸 —— 因为测试没真跑
  • 第二天想改一行 —— 因为没有人（包括 AI）能读懂昨天的实现

Superpowers 是一套把这些坑堵上的流程，不是一个新工具。

7 步流水线（白板版）

 ① brainstorming   设计对话 → 三路分类
 ② git-worktrees   隔离工作区 + 基线全绿
 ③ writing-plans   2-5 分钟一步 · 无 TBD
 ④ subagent / native 执行模式二选一
    │
    ├─ 每个 task：
    │  ⑤ TDD (RED → GREEN → REFACTOR)
    │  ⑥ requesting-code-review
    │
 ⑦ finishing-a-development-branch
    merge / PR / keep · 人选

Step 5、6 是嵌套在 Step 4 里的循环 —— 不是最后补。

三路分类 · 一句话判据

问自己：「这条流程现在在这个 repo 里能读到吗？」

  • 能读到 · 只是改 → Bounded（chat 一段短设计 · STOP · 等 yes · 实现，没有 spec 也没有 plan）
  • 读不到 · 只要答案 → Spike（2-3 句说 probe · 跑一下 · 报告建议 · 代码扔掉）
  • 读不到 · 要留下来 → Architectural（完整对话 → 写 spec 文件 → review → 才叫 writing-plans）

Bounded 度量仓库，不度量任务大小，也不度量你熟不熟。

Plan 的 6 种失败 · 一眼识别

P1TBD / TODO / implement later
P2appropriate / edge cases / as needed
P3"Write tests for the above"（无 code block）
P4"Similar to Task N"（executor 会乱序读）
P5Code step 只说"做什么"不给代码
P6引用了任何 task 都没 Produces 的符号

命中任意一条 → plan 退回。不用继续读。

Subagent 还是 Native

Task ≥ 10Sub
Task 间接口复杂Sub
需要无人值守 2+ 小时Sub
出错代价高（生产 · 迁移）Sub
Token 预算紧张Nat
Task ≤ 5 · 独立 · 设计已定Nat
快速 spike 探索方向Nat

Subagent 不是更高级，是更贵。它用 2× token 换"接口契约"和"上下文不污染"。

Verification Iron Law

NO COMPLETION CLAIMS
WITHOUT FRESH VERIFICATION EVIDENCE

三句实操：

  • 说 "should / probably / 看起来 / 应该 ok" = 红旗 = 还没跑
  • AI 报告 "test pass" 不算证据，看 diff + 本地跑一次
  • 回归测试要双向验证：通过 → revert 修复 → 必须 fail → restore → 通过

PR review 只问一句：「最后一条 commit 之后跑过测试吗？贴一下输出。」

常见抵触 · 应答

"这么小的活也要走完整流程？"三路分类。看 repo 不看大小。
"我 prompt 已经写得很清楚了。"扫 P1-P6 里的 4 个词组，你就知道有没有真清楚。
"AI 说完成了就完成呗。"Iron Law：没跑过的绿灯 = 假绿灯。
"这太啰嗦了，效率低。"前 30 分钟慢，之后 subagent 无人值守跑 2 小时。琐碎改动就别用。
"Subagent 听着高级，都开它。"反过来 —— 它更贵不是更高级。小 plan + 预算紧 = native。

最小行动

试用一周。规则只有一条：

下次让 AI 帮你写代码前 · 先跑一句：
让我们做一个 ...
看 agent 是不是没直接开始写 · 反而问你问题、要求分类。

那一瞬间你会明白 superpowers 到底在做什么 —— 剩下的 6 步之后再说。
