Superpowers · Lesson 0001 · 约 12 分钟

三路分类：Spike / Bounded / Architectural

Agent 想跳过设计直接写代码？——那是你没搞清 superpowers 让它先做的第一件事。

为什么这是第一课

你的使命有两条：用 superpowers 真正做出一个小产品，和把这套方法带进 2–10 人小团队。这两条都撞在同一堵墙上：

Common failure

"我就加个小功能，也要走完整流程？" —— 这是 superpowers 在团队里被否掉的第一句话。

答案不是"要，别偷懒"。答案是「看情况，但情况不是你想的那样」。这个"情况"就是 brainstorming 的三路分类。

本节结束后，你会知道：拿到一个需求，不是问"这大不大"，而是问 "这条流程现在在这个 repo 里能读到吗？"

三条路径 · 60 秒版本

Path A

Spike

要一个答案，不要一段代码。

"能不能做？" / "值不值得？"

2-3 句说清 probe → 点头就跑 → 报告 recommendation。
代码全部标 throwaway。

Path B

Bounded

改的是这个 repo 里已经存在的流程。

加 flag、单文件 fix、给已有 endpoint 补参数。

几个澄清问题 → chat 里一段短设计 → STOP 等 yes → 实现。
没有 spec 文件，没有 plan 文档。

Path C

Architectural

这个 repo 里还没有这条流。

新项目、新子系统、改变组件之间怎么拼。

完整链路：一问一答 → 2-3 方案 → 分段确认设计 → 写 spec 文件 → 用户 review → writing-plans。

决策的一刀

brainstorming 里最反直觉的一条：Bounded 度量的是 repo，不是任务的复杂度，也不是你的熟悉度。

直觉陷阱

你做过 100 个 todo app，但你在这个 repo 里第一次建 todo 功能 —— 它是 Architectural。因为这个 repo 里没有既存流程可以读。

反过来：一个 5000 行代码的巨型服务里，你加一个只影响两三个文件的开关 —— 它是 Bounded。因为流程已经在那儿。

判据只有一条：

"这条流程现在在这个 repo 里能读到吗？"
  • 能读到 → Bounded（改它）
  • 读不到 · 我要的答案是"能不能" → Spike
  • 读不到 · 我要的是能留下来的代码 → Architectural

棘轮规则 & 批准闸门

两个必须一起记住的硬约束：

① 单向棘轮（Ratchet）

任务中途发现隐藏复杂度 → 路径 只能升不能降：Spike → Bounded → Architectural。停下来，公开说出来，重新分类。

② 批准只覆盖"当前这一层"

SKILL.md 的 <HARD-GATE> 说得很直接："A reply approves the stage actually presented." 也就是：

  • 用户批准了 chat 里那段设计 ≠ 批准了 spec 文件 —— 你还没写那个文件
  • 用户批准了 spec 文件 ≠ 批准了 implementation plan —— 你还没写那个 plan
  • 一个任务批准 ≠ 下一个类似任务的预先批准
最容易被 agent 骗过的一刻

Agent 说："设计你看了 ok 对吧？那我开写了。" —— 在 Architectural 路径下这是跳闸门。正确下一步应该是：把设计写成 spec 文件 → 提交 git → 请你 review 那个文件。

Recall 练习

凭记忆作答。答完会立即显示反馈；每一题只允许选一次（这是 recall practice，不是猜谜）。答错不要紧 —— 反馈里会告诉你为什么。

Q1 · 基础判断
在一个还没有任何认证逻辑的新 repo 里，你要加"用户登录"。三路里选哪条？
Q2 · 反转
登录功能已存在，现在给它加一个"4 位 PIN 快捷登录"选项。
Q3 · Spike 判据
"这个附件元数据表用 SQLite 还是 Postgres？做两天能换吗？"你要 agent 帮你回答。
Q4 · 闸门
Architectural 路径下，用户在 chat 里说了"设计 ok"。Agent 下一步该做什么？

Q6 · 布道（mission D）
同事吐槽："就这么个小按钮也要走 superpowers 全套？"你怎么回应最贴合它的哲学？

行动：一个 5 分钟内可完成的动作

Action Step · 今天就做

1. 打开你 下一次 要交给 agent 的任务（不管是 superpowers 项目还是别的）。

2. 在按下回车之前，先在便签上写一行：
Path = ______，因为 ____________________

3. 让 agent 跑 brainstorming（或它自己会调用）。听它说出的分类。

4. 对上了 → 记住这个判据。对不上 → 不要立即反驳，先问它 "你为什么判成 X"，把它给的理由和你写的原因对比。

5. 把结果（3 个任务足够）写在 learning-records 里的第一份记录中。下一节课我会用它校准你的 ZPD。

如何给同事讲这件事（60 秒版）

可复制到 team wiki 的一段话

"Superpowers 不会让 agent 一上来就写代码，但也不是所有事都写 spec。它先问一句：『这条流程我们仓库里现在有没有？』——

  • 没有 · 只是想知道"能不能" → Spike：跑一段实验，出结论，代码扔掉。
  • 没有 · 是要留下来的东西 → Architectural：走完整设计对话，落一份 spec 文件，再排 plan。
  • 有 · 只是改它 → Bounded：几句话说清新行为，你点头，就直接动。

关键是——分类看的是仓库，不是任务大小，也不是我干过没干过。做过的第 101 个登录，只要在这个 repo 里它是全新的，就走 Architectural。反过来，5000 行老服务里加一个开关，也是 Bounded。"
