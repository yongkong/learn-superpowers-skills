Subagent 的 4 个"真停下来"条件

SKILL.md 明列："Four things stop you, and only these." 除这 4 条外，subagent 遇到任何冲突 / 歧义 / plan 缺陷都应自己裁决 · 写进台账 · 继续跑：

  1. 不可逆 / 破坏性操作（比如 drop table · force-push）
  2. 安全敏感动作（比如改权限 · 处理密钥）
  3. Worktree 之外的副作用（merge 到共享分支 · push · publish）
  4. Plan 烂到"任何方向都是猜"

Rulings, not stalls · 台账格式

每次 agent 自己裁决一个冲突，都记入 ledger（progress.md）：

Ruling: <你决定了什么> — <为什么> — <如果错了的代价>

这个"代价"字段很重要 —— 它决定人类回来时是否需要立刻回滚，还是可以让它继续跑完。

Fix Loop（评审没通过时）

Subagent 的 per-task review 是一个 5 轮封顶的循环：

  • Round R ≤ 3：恢复原 implementer subagent，让它继续修（保留它的上下文）
  • Round R ≥ 4：换 更强的 fresh implementer（因为老的可能就是搞不定）
  • Round 5 结束还有 open findings：逐条裁决（adjudicate）。承重问题（load-bearing）→ 停下；其他 → park 进台账继续。

Ledger 与恢复

Compaction 之后

Session compact 之后，相信 progress.md 和 git log，而不是相信 agent 自己的记忆。
台账第一行 # SDD ledger — plan: <plan file path> 是身份标识 —— 如果它指向的是别的 plan，不要读它的进度，另起一份。

什么时候混合用

官方没有明说 "mixed mode"。但一个常见的实用策略：

  • 前期 3-5 个"骨架 task"：用 subagent · 因为接口设计定生死
  • 后期"重复性" task（比如给 20 个 model 都加一样的 validator）：切 native · 因为每个 task 判断都类似，污染风险低

这个策略需要你在 Step 4 中途切档 —— 记得让 agent 明说"前 5 个 task 用 subagent，后面切 native"，写进 plan 尾部。
